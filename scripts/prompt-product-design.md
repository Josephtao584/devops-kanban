# Prompt 1：产品设计（产品经理视角）

两段式设计流程的第一步。跑完这步得到产品设计文档后，再用 `prompt-architecture-design.md` 让架构师基于它出架构设计。

把下面整段发给 LLM（如 `claude`），并在 `{在这里写你的需求}` 位置填入具体需求。

AI 会按需读取系统资料了解现有功能边界，但输出是**产品设计文档**（不是架构设计），内容保存到本地 `service-analysis/designs/` 下。

---

```
你是一位资深产品经理。我给你一个新需求，请帮我输出一份产品设计文档。

## 你有的资料（用来判断功能边界和已有能力，不要把技术细节写进文档）

- service-analysis/architecture.md   —— 系统总览，先读这个了解我们有哪些模块/服务和它们对应的业务能力
- service-analysis/profiles/*.md     —— 每个服务的画像，读里面的"职责/业务能力"而不是"接口/表结构"

## 工作流程（请严格按顺序）

1. 先用 Read 读 service-analysis/architecture.md，建立对现有系统能力的整体认知
2. 根据需求判断可能涉及的业务模块，用 Glob 列出 service-analysis/profiles/ 下的文件做校对
3. Read 相关 profile，关注"它承担什么业务"，忽略技术栈和接口细节
4. 若发现关联模块遗漏，回到第 3 步补读
5. 开始撰写产品设计文档

## 新需求

{在这里写你的需求}

## 输出方式

**不要把文档打印到 stdout**，而是用 Write 工具保存到：

    service-analysis/designs/<需求简短英文/拼音slug>.md

slug 由你根据需求内容命名，小写、用 `-` 连接，例如 `user-points-system.md`。
若目录不存在请先创建。保存完成后在 stdout 里只回复：

    已生成: service-analysis/designs/<文件名>

## 设计文档结构（产品视角，非技术细节）

### 一、需求背景
这个需求从哪里来、要解决什么问题、不做会怎样。2-4 句话讲清楚。

### 二、目标与非目标
- 目标：这次要达成的业务结果（可衡量优先）
- 非目标：明确不在本次范围内的事（防止范围蔓延）

### 三、用户与场景
- 目标用户是谁（角色/画像）
- 典型使用场景描述（用"当 …… 时，用户 ……"句式）

### 四、功能范围
列出本次要新增或调整的功能点。每条写：
- 功能名
- 所属模块（对应现有哪个服务/页面，引用 architecture.md 或 profile 里的名字即可，不要写接口/表）
- 是"新增"还是"调整"
- 一句话描述

### 五、核心流程
用步骤化的方式描述用户操作路径和系统反馈，如：
1. 用户在 X 页面点击 Y
2. 系统展示 Z
3. 用户 …… 则 ……，否则 ……

覆盖主流程 + 关键分支（权限不足、数据为空、失败重试等用户能感知的分支）。

### 六、交互与信息结构要点
不画 UI 稿，但要说明：
- 新增/改动的页面或入口位置
- 关键字段或展示信息
- 空状态、加载态、错误态的产品侧预期

### 七、验收标准
Given/When/Then 写法，每条可测。例如：
- Given 用户未登录，When 访问 X，Then 跳转登录页

### 八、关联影响（产品层）
- 对现有功能的影响（会不会改变老用户的使用习惯）
- 数据/权限/计费口径层面需要产品确认的事（不要写技术实现）

### 九、风险与待决问题
- 产品风险：可能引起的用户误解、流失、合规问题等
- 待决问题：需要跟业务方/老板/法务/设计再确认的 open question

## 硬性要求

- 只依据上述资料推断现有系统的能力边界，不要臆造功能或模块
- 文档中引用已有模块时用 architecture.md / profile 中出现过的名字
- **不要**写接口、表结构、RPC、技术选型，这些是架构师后续的事
- 如果需求本身就不清晰，在"九、待决问题"里列出你需要产品经理再给你澄清的点
```
