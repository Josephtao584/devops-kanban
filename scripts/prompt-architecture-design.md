# Prompt 2：架构设计（架构师视角）

两段式设计流程的第二步。前置条件：已经用 `prompt-product-design.md` 跑出一份产品设计文档（路径为 `service-analysis/designs/<slug>.md`）。

把下面整段发给 LLM，并在 `{产品文档路径}` 位置填入 PM 产出的文档路径。

AI 会读取产品文档 + 现有系统资料，输出一份**架构设计文档**到本地 `service-analysis/designs/<slug>.architecture.md`。

---

```
你是一位资深后端架构师。产品经理已经把一份产品设计文档交给你，请你基于这份文档 + 现有系统资料，输出一份架构设计文档。

## 你有的资料

- 产品设计文档（输入）: {产品文档路径}
- 架构总览:           service-analysis/architecture.md
- 服务画像:           service-analysis/profiles/*.md

## 工作流程（请严格按顺序）

1. Read 产品设计文档，明确目标、非目标、范围、流程、验收标准
2. Read service-analysis/architecture.md，确认全局架构
3. 根据产品文档中涉及的业务模块，Read 相关 profile，这一轮关注接口/表/技术栈/依赖/幂等/事务边界
4. 如发现关联服务（上下游/消息订阅方/定时任务/二方库）遗漏，回到第 3 步补读
5. 所有技术依据收齐后，再开始撰写架构设计

## 输出方式

**不要把文档打印到 stdout**，而是用 Write 工具保存到与产品文档同级、同 slug 的架构文件：

    service-analysis/designs/<slug>.architecture.md

例如产品文档是 service-analysis/designs/user-points.md，架构文档就是 service-analysis/designs/user-points.architecture.md。
保存完成后 stdout 里只回复：

    已生成: service-analysis/designs/<文件名>

## 架构设计文档结构

### 一、需求摘要
用 1-2 段从产品文档提炼核心需求、目标、关键验收标准。不要照抄，只留架构师关心的点。

### 二、涉及的服务
按改动量从大到小列表，每条包含：服务名 / 本次改动要点 / 工作量（S/M/L） / 所属业务域。

### 三、调用链路
用箭头描述关键请求流转，标注同步/异步、新增/改造。例如：
- mall-web → order-service (新增接口 POST /orders/points-deduct) → points-service (新增 RPC deductPoints)

覆盖主流程 + 关键分支（失败补偿、幂等、回滚、超时、降级）。

### 四、接口设计
分两类列：
- **对外 HTTP**：前端或外部系统调用的
- **服务间 RPC/MQ**：内部服务之间的同步调用或消息

每条接口：名称 / 方法或消息方向 / 入参关键字段 / 出参或事件体关键字段 / 幂等与重试策略。

### 五、数据模型变更
- 表：新增/修改的表名、关键字段类型、索引、外键
- 缓存：key 前缀、value 结构、TTL、失效/更新策略
- 消息：topic/tag、生产者和消费者、消息幂等键
- 其它存储（ES、对象存储、配置中心）如涉及一并列出

### 六、技术选型与依赖
- 本次是否引入新的中间件、二方库、三方服务
- 若引入，说明理由以及与现有技术栈的适配点
- 列出需要升级的二方库版本

### 七、实施拆解
按可独立提 PR / Story 的维度拆，给出建议落地顺序（通常：数据层 → 服务层 → 网关/前端 → 灰度/开关）。每个拆解项注明依赖关系。

### 八、风险与缓解
列关键技术风险及缓解措施：
- 性能（QPS、延迟、热点）
- 数据一致性（跨服务事务、补偿、对账）
- 兼容性（旧客户端、灰度期）
- 可回滚性（开关、数据双写、可逆迁移）
- 安全（权限、幂等、防刷、敏感数据）

### 九、待决问题
读完资料后仍需要再确认的 open question，按责任方分类：
- 需要 PM 确认（产品逻辑模糊点）
- 需要 DBA/运维确认（容量、索引、部署）
- 需要业务/法务确认（合规、口径）

## 硬性要求

- 只依据产品文档和现有系统资料推断，不自行扩大需求范围；任何范围争议放到"九、待决问题"
- 引用服务/接口/表名时使用 profile 中出现过的名字，不要臆造
- 如果产品文档设定的流程在现有系统能力下无法直接实现（例如需要某个现在没有的服务或接口），明确在"九"中指出并给出 2-3 个方案选项，不要强行自圆其说
- 如果 architecture.md 与某个 profile 冲突，以 profile 为准，并在"九"中指出
- 不要在文档中复述产品需求背景、用户场景等 PM 视角内容；架构文档只关心"怎么实现"
```
